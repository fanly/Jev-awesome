# Jev 到底适合放在你的程序哪一步？

如果你只记住一句话：**Jev 适合「在有限选项里做校准判断」的那一步，不适合「从零写出长文本」的那一步。**

## 先画你的控制流

多数应用可以粗分成：

1. **感知 / 收集**：页面 DOM、手机截屏、数据库行、工单原文、图上的出边……
2. **决策**：在候选动作、标签、路由、下一跳里选一个（或给出概率）
3. **生成**：写邮件、填表单字符串、解释理由、渲染回复
4. **执行**：点击、SQL、发消息、改状态机

Jev（System One）主要吃第 2 步：你给出 `state` 和 typed `questions`（`Choice` / `Noul` / `Score`），它返回结构化答案与概率。它**不**替你完成第 3 步的散文生成。

把第 2 步和第 3 步绑在同一个「大模型随便说说」里，常见后果是：动作空间失控、难测、难审计、难限流。

## 放对位置的例子

| 场景 | Jev 放哪 | 别让它干什么 |
|---|---|---|
| 浏览器 Agent | 从当前元素表里选 `CLICK` / `TYPE_TEXT` / … | 不要让它顺便编城市名；`TYPE_TEXT` 再交给文本模型 |
| 客服分流 | 部门 `Choice` + 是否加急 `Noul` | 不要让它直接写完整回复正文（除非你另有生成链路） |
| SQL / 图查询 | 行/边是否满足自然语言条件 | 不要用它替代查询规划器去「编 SQL」 |
| 安全护栏 | 是否违规 / 选哪条策略 | 不要指望单次判断等于完整合规体系 |

## 什么时候先别上 Jev

- 你还没有**离散候选**（选项是开放集合，或每天变几千个无法枚举）
- 你真正要的是**长文写作**或创意生成
- 你还没想清楚失败时人工如何接管（低置信 / `BLOCKED` / 拒绝）
